<plan_corrections>
Corrections made while executing, with the reason for each:

- Test location. `analysis_neutral` and `ts` are crate-private, so an
  integration test under `crates/polint/tests/` cannot build solver inputs
  without widening the public surface. The fixtures are an in-crate test module,
  `ts/points_to/solver_composition.rs`, run with
  `cargo test -p polint --lib solver_composition`. Every verify command that
  says `--test solver_composition` means that filter.
- Budget split. `SolverBudget.max_steps` (10,000) also bounds the engine's
  `derive_edges` closure, which this plan does not touch. The points-to step
  ceiling becomes its own field, `PointsToSubBudget.max_steps`, with the new
  default of 50,000,000; `SolverBudget::points_to_budget()` reads it, and the
  cache key names it. `SolverBudget.max_steps` keeps its value.
- Call rule inputs. The call rule runs on two solver inputs, calls and function
  signatures, instead of two new `PointsToConstraintKind` variants. That enum is
  the stored points-to fact family: the kernel validates it and the type
  provider serialises it. The call shape is stored where the rest of the
  graph's constraints are, in `ConstraintKind::CallConstraint`, and projected
  into solver calls by `ts/points_to.rs` for each solve.
- Callee variable. The callsite node stays the variable whose set gives a
  site's targets, because the walker and the object model write into it.
  `CallConstraint.callee` names the callee place, and the projection adds
  `Copy(callsite <- callee)`.
- Heuristic taint. With the latch gone, the solve runs on axios, async and zod
  for the first time, and an edge the call rule derives from a walker row
  would otherwise be an exact claim. The solver carries, per variable, whether
  any `Heuristic` constraint fed it, through copies, field slots and the call
  rule. A tainted set is `Heuristic`, and so is every edge read from it. The
  taint is per variable, not per object: a set fed by both a walker row and an
  exact path is heuristic as a whole. This costs exact recall at such sites and
  never adds an exact claim.
- Parameter places. MIR parameter indexes skip destructured parameters, and
  `ts/mir/lower.rs` is outside this plan. So this plan does not project
  `Copy(param place <- FunctionParam)` from MIR; lowering parameters is the
  next plan's work. Real builds get `FunctionThis` and `FunctionReturn` nodes
  for every TS function, and `FunctionParam` and `FunctionRest` nodes only
  where a projection needs them (none yet). The call rule is proven on the
  fixtures with all four kinds. The must-have "one parameter place per
  position" is met by the node kinds and the solver, not by real builds yet.
- CallConstraint projection. TS MIR lowers callees as source text, so real
  call facts carry argument and result places and rarely a callee place.
  `project_call_edges_and_constraints` fills `callee`, `receiver` and `result`
  from the `CallSiteFact` where the place has a node. It leaves `arguments`
  empty: MIR drops an argument that lowers to no place and records a spread
  with no position, so a MIR argument index is not a position, and binding by
  it would pass a value to the wrong parameter. Positional arguments come with
  parameter lowering. The other `CallConstraint` pushers (direct bindings, the
  walker and the object model) pass only the callsite. Place filling is TS
  only; Go call constraints keep the callsite alone.
- Return places in real builds. `Copy(FunctionReturn <- returned place)` is
  pushed at `SummaryProjected` precision, which the refined-call reader maps to
  `Heuristic`. A call resolved through a value a function returns is therefore
  never an exact claim until returns are proven by the lowering plan.
- `go/` touched mechanically. `CallConstraint` gained fields, so the Go
  projection and the Go RTA reader match it with `{ callsite, .. }` and build
  it with `ConstraintKind::call_at`. No Go behaviour changes.
- Spread and rest. Arguments from `spread_from` on are not bound; parameters
  at or after that position, and every rest place of a call that passes
  arguments, are marked incomplete through a `Heuristic` dependency. There is
  no array element model, so a rest parameter never receives a value.
- Binding provenance. Each variable keeps at most four binding provenances,
  the smallest by resolved text, joined along copies. A capped join is still a
  semilattice join, so the result does not depend on constraint order.
- Partial status. A set is `BudgetExceeded` when its variable is still pending
  when the solve stops, or is reachable from a pending variable through copy
  edges, field-load and field-store slots, and call-rule targets. Every other
  set is `Present`. `PointsToSetFact.budget` stays the run-level status,
  because the Go refined-call reader keys on it.
- Order independence. The solver sorts its constraints by kind and resolved
  stable key before the solve, and gives each field slot a variable id from a
  hash of `(object, field)` instead of from encounter order.
- Inputs the solve cannot see. Once sets survive the solve, a field slot the
  object model writes from an unresolved value (a synthetic write-source place
  that no constraint defines) held only the function written beside it, and
  that singleton was an exact claim. The held-out gate showed it: one wrong
  exact target and one false-complete site on node-forge, found from engine
  output alone. The plan assumed an empty set means "no value"; it means "no
  value the constraints describe". The solver now marks a set open when it can
  be reached from a variable read as a source that nothing defines, or from
  the result of a call whose callee set is empty or holds an object without a
  signature, spreading like incompleteness, and raises every open set to
  `Heuristic`. Targets stay, below the exact tier. Fixture:
  `input_the_solve_cannot_see_keeps_edges_out_of_the_exact_tier`. The rule is
  in the engine, not the TS frontend, because a parameter nothing binds and an
  unresolved call result have the same flaw.
</plan_corrections>
