# Next structural lever: canonical identity sharing

The retained Excalidraw profile (MIT, commit 0dbd2a39319d41fda37b2945dea0dcbd58d6a564) ends with 2,505,876 interned keys containing 3,085 MiB of text, for only 2,566,051 input source bytes. The data-flow stage spends 2.755 s digesting and 2.705 s storing metadata after local and direct-call construction together fall below one second. Evidence digesting still consumes 6.580 s. These are single-run provider timings, not a new speedup claim.

`internal_core/stable_key.rs` interns complete `Arc<str>` texts. `analysis_api/metadata.rs::stable_key_from_parts` formats a complete canonical string before interning. Composite keys include previously expanded parent keys, so interning identical complete strings does not share common substructure between distinct keys. This is structural retained memory, not merely temporary allocator churn.

A follow-up experiment should represent composite identities as interned nodes containing a family and a frozen sorted list of literal/child-key parts. Keep dense run IDs in the same insertion order. Track canonical encoded lengths on nodes and stream the existing canonical byte representation into digest consumers. Preserve textual ordering using chunked comparison and reusable lexical ranks; numeric IDs cannot substitute for text ordering. Materialize text only at boundaries that actually require it. Atom/child equality must be collision checked, and backslash normalization plus byte-length prefixes must retain their present semantics.

Required proof before adoption: old/new canonical byte streams and digests equal for every fact family; duplicate identity and sparse-ID behavior unchanged; no change to capped uncertainty or diagnostics; original pinned accuracy gates unchanged; measured warm/cold memory and wall time. Start behind a private representation boundary, not an SDK change. Existing callers returning `Arc<str>` and full text sorting are real migration work; simply replacing the interner with another hash-map crate will not remove the recursive text expansion.

The current solver is under three percent of the reduced Excalidraw wall time. A solver-only rewrite cannot deliver another large end-to-end gain there. Go profiling additionally points to symbol graph construction and large CFG materialization; re-profile a completed, uncontended Go run before extrapolating the Excalidraw result. No end-to-end 10× result has been demonstrated.

The guarded Hugo cold run on September 7 confirms a separate Go limit: the symbol stage took 120.135 s and its cached diagnostics explicitly say `GoSubprocessTimeout: Go symbol sidecar exceeded its 120000 ms timeout`. The code retains `GO_SUBPROCESS_TIMEOUT = Duration::from_secs(120)` in `go/process_runner.rs`. This is failed sidecar setup, not CPU attribution for graph construction. Preserve the failure in the before/after comparison and investigate loading/sidecar setup before extrapolating Go analysis coverage or healthy-runtime speedups. Evidence is in `hugo-symbol-sidecar-diagnostics.json`. Hugo is Apache-2.0 at 3f35721fb2c75a1f7cc5a7a14400b66e73d4b06e.

That first Hugo attempt was subsequently excluded by the external-compiler guard. Its retry produced a different setup diagnostic: a generated Go build file outside the repository. Do not treat the excluded timeout observation as an accepted headline sample. Diagnose setup variability and require identical provider/diagnostic outcomes before accepting any paired Go comparison.

A separate Go architecture candidate is shared package loading for combined symbol and semantic requests. Both `go-sidecar/polint-go-symbols/internal/symbols/emit.go` and `go-sidecar/polint-go-frontend/internal/semantic/emit.go` call `packages.Load` with the same root/lifecycle model in separate processes. This is source evidence of duplicated loading, not a measured speedup. The loaders are not interchangeable: the symbol sidecar pins x/tools 0.42.0, the semantic frontend pins 0.45.0, and only the latter requests `NeedDeps` before building full SSA with generic instantiation. Do not remove `NeedDeps`; its existing invariant prevents incomplete dependency SSA and RTA failures. A unified private frontend could reuse one sufficiently rich load only when both views are requested, preserving module roots, tests, patterns and build tags. Align tool versions and source/generated-file handling under the unchanged accuracy gates before claiming any gain. Symbol-only requests should retain their cheaper lifecycle. This is follow-up work, excluded from the retained patch.


## Memory-limit evidence and migration hazards

The final golang/tools attempts (BSD-3-Clause, commit 7743a285e3d261ca235408e013ec5c14cb5170e4) both ended with SIGKILL before type/value analysis completed. At the last completed provider they already held 4,025,109 interned keys with 4,050 MiB of text. The container has a 12 GiB memory limit and six-CPU quota, below the visible host resources. The container-wide OOM counter increased during the optimized attempt; it does not identify a killed PID. These are failed attempts, not completed wall-time/RSS measurements. This makes bounded identity representation a capacity issue as well as a speed target. See `container-limits-and-tools-failure.json` and `tools-partial-provider-equivalence.json`.

Canonical-byte identity, not structural tuple identity, is the compatibility boundary. A raw literal and a composite node can encode identical bytes; different chunk boundaries must intern to the same ID. Hash the canonical stream, then compare streamed bytes to resolve collisions and alternate representations. Preserve insertion IDs, stable ordering among duplicate part labels, UTF-8 byte lengths, and backslash normalization. Cache encoded lengths with checked arithmetic and use iterative traversal so nested input does not consume an unbounded call stack. The existing `Arc<str>` resolver contract will materialize text for every unmigrated caller, so measure that materialization count and retained bytes before claiming a memory improvement.

Sharing structure removes repeated allocation and storage; streaming alone still visits every encoded byte. It therefore does not guarantee a 10x end-to-end gain. Digest-prefix reuse is possible only where the concrete hash API and shared canonical prefixes support it without changing digest bytes. Do not substitute structural hashes for the current canonical payload digests. A first prototype should keep the existing public resolver, add private streaming comparison/digest methods, migrate metadata and the hottest internal consumers, and differentially test raw-versus-composite equivalence plus all existing accuracy cases before expanding scope.

## Exact composable FNV summaries: a checked follow-up hypothesis

The concrete digest implementation in `analysis_api/digest/mod.rs::fingerprint_byte` is byte-wise FNV-1a: `h = (h XOR byte) * p mod 2^64`, with `p = 0x100000001b3`. The older `cache::stable_hash` uses the same recurrence. This permits a reusable transformation for an arbitrary byte fragment, including when its incoming hash state varies. It does not require that fragment to be a common prefix.

For a fragment of length `n`, define `s = p^n mod 2^64` and a 256-entry correction table `d[r] = F(r) - s*r mod 2^64`, where `F` hashes that fragment starting in state `r`. Then its exact action on any 64-bit state is `F(h) = s*h + d[h & 255] mod 2^64`.

Proof: two input states differing by a multiple of 256 have identical low bytes. XOR with a byte preserves their arithmetic difference, and multiplication scales it by `p`. Induct over the fragment's bytes to obtain `F(h) - F(h & 255) = s*(h - (h & 255))`. All arithmetic is modulo 2^64, so overflow preserves the identity. A fragment summary therefore applies with one indexed table read, multiplication and addition. Two summaries compose by evaluating the right summary on each of the left summary's 256 residue outputs and multiplying their scales. Composition costs 256 evaluations regardless of the expanded fragment lengths.

The standalone Python experiment `fnv_chunk_proof.py` passed 22,776 byte-stream equivalence checks and 128 composition-associativity checks, including every low-byte residue, random full-width states, empty fragments, zero/0xff bytes, UTF-8/escaping, exact digest length framing, and repeatedly shared children up to 36,864 expanded bytes. The algebra supplies the general argument; these checks are corroborating evidence. Results are in `fnv_chunk_proof.json`. This is correctness research only: no Rust implementation, production integration, or speed measurement is included in the retained patch.

Costs prevent indiscriminate use. A table alone is 2 KiB; storing one for all 2.5 million Excalidraw keys would consume roughly 4.8 GiB, exceeding their current text storage. Summarizing a raw literal naively takes 256 passes. An adaptive DAG prototype should summarize long, repeatedly used composite children, reuse existing child summaries, and stream small literals. Preserve separate summaries for raw canonical bytes and escaped encodings if both are needed. Length framing and separators remain exactly as today. Full canonical equality/order comparisons and currently materializing callers still need migration; this technique accelerates compatible digest consumption, not every interner operation. Keep the interner's collision-resistant lookup behavior and canonical collision checks: do not replace its randomized map hashing with this predictable digest to save a traversal. Measure the reuse distribution, table construction cost and retained table bytes before adoption.
